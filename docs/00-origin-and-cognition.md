# 00｜起源与认知形成过程

这份文档不只记录“现在怎么做”，而是保留这套 Android 自动化方案是怎样一步步形成的。

原因很简单：如果以后只留下最终架构，新窗口或新模型很容易把它重新理解成“一个 AutoJs6 脚本仓库”，然后把已经排除过的错误路线重新做一遍。

---

## 1. 起点：这台 K20 Pro 到底算什么

最初的问题不是“写脚本”，而是：

> 一台 Redmi K20 Pro，Root、固定供电、24 小时在线，除了挂游戏和抢券还能怎么玩？

讨论中逐渐形成的判断是：

它已经不再像一台普通个人手机。

更接近：

```text
带屏幕 / 触摸 / 摄像头 / 麦克风 / Wi-Fi / 蓝牙 / 传感器
+
Android App 生态
+
Root
+
长期固定供电
=
一个廉价但功能丰富的 Android 边缘自动化节点
```

“安卓工控机”是方便理解的比喻，但不是严格工业设备。

真正有价值的特征不是“性能强”，而是：

- 真 Android 环境；
- 能直接运行目标 App / 游戏；
- 自带完整输入输出；
- Root；
- 固定设备；
- 长时间在线；
- 不承担个人主力手机职责。

这使它特别适合做一个长期自动化节点。

---

## 2. 从“旧手机玩法”转向“无人值守节点”

一开始讨论了很多可能玩法：

- 游戏挂机；
- App 签到；
- 优惠券；
- 网络巡检；
- Android 真机实验节点；
- 自动截图 / 录屏；
- 小型 HTTP / 文件服务；
- 蓝牙 / Wi-Fi 网关；
- 远程观察节点。

但继续讨论后，真正值得做的主线逐渐收缩成：

> 把重复、确定、可恢复的 Android 操作交给它长期执行。

尤其是游戏场景。

低级自动化只是：

```text
固定坐标
→ 点击
→ 等待
→ 再点击
```

成熟自动化则会变成：

```text
判断当前状态
→ 选择下一步
→ 执行
→ 验证
→ 失败恢复
→ 保存状态
→ 等下一任务
```

从这里开始，项目目标从“脚本合集”变成了“Android Automation Node”。

---

## 3. 对游戏挂机能力上限的重新认识

讨论“大家能把挂机做到什么程度”后，形成了一个重要分层：

```text
宏 / 连点
↓
Accessibility UI 自动化
↓
截图 / 模板 / OCR
↓
状态机
↓
定时调度
↓
Watchdog + Recovery
↓
专用游戏机器人
```

真正难的不是“点哪里”。

真正难的是：

- 断网怎么办；
- 游戏闪退怎么办；
- App 卡死怎么办；
- 页面加载时间变化怎么办；
- 突然出现活动公告怎么办；
- 任务中断后怎么继续；
- 自动化自身死掉怎么办；
- 一周之后它还能不能正常跑。

因此项目认知从：

> 能否自动点击？

变成：

> 能否长期无人值守，并在普通故障后自己回到任务轨道？

这也是后来 Supervisor / Watchdog / Recovery 成为核心的原因。

---

## 4. AutoJs6：从“主角候选”变成“通用运行时”

最初考虑 GKD。

进一步阅读后确认：

- GKD 不是单纯坐标点击器；
- 它是基于 Accessibility 树的状态化规则引擎；
- 适合“出现 A → 做 B”；
- 有 selector、动作、冷却、计数、前置规则、snapshot、Inspect HTTP 服务等；
- 很适合简单响应式 UI 自动化。

但对于：

- 循环；
- 分支；
- 持久状态；
- 定时调度；
- 游戏截图识别；
- 多步骤恢复；

GKD 的表达方式并不是最自然的。

于是 AutoJs6 进入视野。

AutoJs6 的意义在于：

```text
Accessibility
+
截图
+
模板匹配
+
OCR
+
Root / shell
+
JavaScript 状态机
+
本机长期运行
```

这更像一个“可编程 Android 自动化运行时”。

但继续研究游戏社区后，又得到第二个修正：

> AutoJs6 适合自己写通用任务，但不应该拿它重写已经成熟的专用游戏机器人。

所以 AutoJs6 的最终位置变成：

- Supervisor 的一个候选运行底座；
- 拼多多等自定义任务的执行环境；
- 没有成熟上游的 App / 游戏任务的通用工具；
- 不是所有游戏逻辑的统一重写目标。

---

## 5. 为什么 PC 不能成为主脑

中间一度出现过另一个架构：

```text
Windows + Codex + Python
        ↓
ADB / uiautomator2 / Airtest
        ↓
K20 Pro
```

从纯技术能力看，这很强。

但现实约束否定了它作为长期运行架构：

- Windows 机器性能一般；
- 不希望为了手机挂机长期维持复杂 PC 栈；
- Codex 有实际使用额度约束；
- Codex 适合开发和调试，不可能成为 24×7 runtime brain。

因此形成了当前非常重要的原则：

> **Windows / Codex 负责开发、排错、部署；K20 Pro 自己负责长期运行。**

最终变成：

```text
开发期：
Windows + Codex
  ├─ ADB
  ├─ scrcpy（需要时）
  ├─ uiautomator2（需要时）
  └─ Airtest/OpenCV（需要时）

运行期：
K20 Pro
  ├─ Supervisor
  ├─ 游戏执行器
  ├─ 拼多多任务
  ├─ Watchdog
  └─ Recovery
```

电脑关掉后，节点仍然应该继续工作。

## 6. 搜索社区后，游戏路线发生了第二次修正

### 6.1 《碧蓝航线》

搜索后确认成熟项目：

- LmeSzinc/AzurLaneAutoScript（Alas）

Alas 已经不是简单脚本，而是一套成熟的碧蓝航线机器人：

- 主线；
- 活动；
- 委托；
- 科研；
- 后宅；
- 战术学院；
- 商店；
- 大世界；
- 心情控制；
- 任务调度；
- 海图识别。

这意味着：

> 从零用 AutoJs6 重写《碧蓝航线》自动化，属于重复造轮子。

Alas 原始架构通常是：

```text
Python 主控
→ ADB
→ 模拟器 / Android 真机
```

问题在于用户不希望电脑长期运行。

继续搜索后发现，历史上确实存在：

```text
Android 手机上运行 Linux/Python 环境
→ Alas
→ localhost ADB
→ 控制同一台 Android 手机上的碧蓝航线
```

尤其旧 Android / Snapdragon 855 一代曾有人成功运行。

于是当前目标不是重写 Alas，而是：

> 研究如何让当前 Alas 在 K20 Pro Android 9 / ARM64 / Root 上本机化。

---

### 6.2 《棕色尘埃2》

搜索后发现：

- sunyink/MFABD2

它基于 MaaFramework，而且已经提供 Android ARM64 APK。

当前官方路线明确支持：

- Android 9+；
- ARM64；
- Root 或 Shizuku；
- 手机本机安装运行。

这和 K20 Pro 的条件高度吻合。

因此这里的判断更明确：

> 不重写。优先直接安装 MFABD2 Android 版。

如果后面出现：

- K20 Pro 特有兼容问题；
- MIUI 10 问题；
- 需要 Supervisor 暂停 / 恢复接口；
- 我们确实需要修改程序；

才 fork。

## 7. 拼多多让“统一调度器”成为刚需

拼多多百亿补贴会员的任务现实是：

- 每天 09:00、16:00、21:00 刷新；
- 一天只能兑换一张；
- 目标是 5 元无门槛券；
- 100 积分兑换；
- 到点页面不会自动刷新；
- 必须手动下拉刷新；
- “积分兑券”模块会因为上方随机模块插入而上下移动。

最初直觉是：

```text
OCR
→ 找文字
→ 点击
```

但进一步讨论后发现，抢券是低延迟任务，整屏 OCR 很可能不应该处于关键路径。

于是策略改成：

优先级：

```text
1. Accessibility 节点
2. 局部模板匹配 / 多点颜色
3. 模块定位后的相对坐标
4. OCR 兜底
```

同时意识到真正的大延迟可能不是最终 tap，而是：

```text
下拉释放
→ 请求发出
→ 服务端返回
→ 页面重绘
→ 目标出现
```

因此后面要实测每一段延迟，而不是凭感觉优化。

## 8. 为什么最后一定需要 Supervisor

用户提出了一个看似简单的问题：

> 抢券前停止游戏挂机，抢券后继续挂机，需要什么？看门狗吗？

这个问题最终让架构定型。

Watchdog 只能解决：

> 任务死了没有？死了拉起来。

但这里还需要：

```text
到时间
→ 抢占屏幕
→ 暂停当前游戏
→ 保存必要状态
→ 打开拼多多
→ 抢券
→ 验证成功/失败
→ 恢复之前的游戏自动化
```

所以真正需要的是：

> **Supervisor / 总调度器**

Watchdog 只是 Supervisor 的一个组成部分。

由此形成当前总结构：

```text
Supervisor
├─ Scheduler
├─ Task Lock
├─ Persistent State
├─ Watchdog
├─ Recovery
├─ PDD Task
├─ Game adapters
└─ Logs
```

---

## 9. 为什么只建一个主仓库，不先 fork 三个上游

最后讨论了仓库策略。

错误路线是：

```text
先 fork AutoJs6
先 fork MFABD2
先 fork Alas
然后再想怎么整合
```

这会让维护负担立刻爆炸。

当前原则是：

> **我们拥有编排层，上游拥有专业执行器。**

所以先建立：

```text
Penrix/android-automation-node
```

负责：

- 设备事实；
- Supervisor；
- 状态；
- 调度；
- 拼多多；
- 游戏接入适配；
- Watchdog；
- Recovery；
- 日志；
- 认知和决策。

而：

- AutoJs6；
- MFABD2；
- Alas；

先直接复用官方上游。

只有出现真实修改需求时才 fork。

---

## 10. 当前认知的最短表达

如果以后只能保留几句话，应该保留这些：

1. K20 Pro 不是普通挂机手机，而是第一台长期在线 Android Automation Node。
2. 电脑和 Codex 是开发工具，不是运行依赖。
3. 长期自动化的核心不是点击，而是调度、状态、恢复和故障处理。
4. Supervisor 是顶层；Watchdog 只是其中一部分。
5. 游戏优先复用成熟专用机器人，不用 AutoJs6 重写一切。
6. MFABD2 优先直接跑 Android APK；Alas 优先研究本机化。
7. 拼多多抢券是低延迟任务：Accessibility / 模板优先，OCR 兜底。
8. 不提前 fork；出现真实修改需求再 fork。
9. 固定设备、固定 ROM、固定分辨率不是缺点，而是自动化确定性的来源。
10. 文档必须保留“为什么变成这样”，避免后续重新走已经排除过的路线。

## 11. 后续纠正：运行边界继续收窄

后续按 coding skill 和真实上游继续审查后，两处早期认知被修正：

### Supervisor-first 被继续减负

早期曾认为需要：

```text
Supervisor
├─ Scheduler
├─ Task Lock
├─ Watchdog
└─ Recovery
```

后续源码审计发现：

- AutoJs6 自带持久 TimedTask；
- MFABD2 自带自己的 schedule / foreground keep-alive / watchdog；
- Alas 自带成熟任务调度。

因此当前不再实现常驻自研 Supervisor。

项目首版只保留真正缺失的“跨应用抢占”：

```text
PDD prepare time
→ 让当前游戏执行器让出手机
→ PDD
→ 恢复原任务
```

### 断电恢复不属于当前目标

Owner 明确：

```text
K20 不会来电自动开机
断电后由 Owner 手动开机
项目不需要解决来电自启
```

因此软件运行边界从“Owner 手动开机、Android 可用”之后开始。

不做 charger-mode、bootloader/init、UPS 或无人冷启动恢复。

这两处修正保留在历史中，是认知形成的一部分；当前实施以最新文档为准。
