# 03｜拼多多百亿补贴会员抢券：现实与设计

## 任务现实

目标页面：

> 拼多多 → 百亿补贴 → 百亿补贴会员 → 打卡 / 积分兑券

已知业务规则：

- 每天刷新时间：09:00、16:00、21:00；
- 一天只能兑换 1 张；
- 目标券：5 元无门槛券；
- 兑换价格：100 积分；
- 到点页面不会自动刷新；
- 必须手动下拉刷新；
- “积分兑券”模块位置不固定；
- 模块上方会随机插入不同内容，导致模块整体上下移动。

因此：

> 固定屏幕坐标不是可靠主方案。

---

## 1. 最初错误直觉：整屏 OCR

一开始很容易想到：

```text
刷新
→ OCR 整屏
→ 找“5元无门槛”
→ 找“100积分”
→ 找“兑换”
→ 点击
```

问题：

- OCR 初始化有成本；
- 全屏 OCR 有额外延迟；
- 文本识别不是抢券真正需要的信息；
- 页面布局虽上下移动，但模块内部结构可能稳定；
- OCR 容易受字号、渲染、抗锯齿、动画影响。

所以当前结论：

> **OCR 不能作为低延迟关键路径的第一选择。**

它应该作为兜底。

---

## 2. 当前识别优先级

### A. Accessibility 节点

第一选择。

实机需要检查：

- “5元无门槛”是否暴露为 text；
- “100积分”是否暴露；
- “兑换”是否是 clickable node；
- 券卡片之间能否通过 parent / sibling 关系定位。

如果节点质量好：

```text
find("5元无门槛")
→ 找同一卡片
→ 找兑换节点
→ click
```

模块上下移动完全不影响。

---

### B. 局部模板匹配

如果 Accessibility 很差：

```text
截图
→ 只截可能出现“积分兑券”的区域
→ 找稳定模板
→ 得到模块坐标
```

稳定模板可以是：

- “积分兑券”标题；
- 兑换按钮图形；
- 5 元券卡片稳定视觉元素；
- 其他独特图案。

AutoJs6 本身有截图和模板匹配能力。

---

### C. 模块位置 + 相对坐标

如果券卡片内部布局稳定：

```text
module = locateModule()

tap(
  module.x + dx,
  module.y + dy
)
```

真正随机的只是：

```text
module.y
```

而不是按钮在模块内部的位置。

这比 OCR 全屏找字更直接。

---

### D. 多点颜色 / 特征点

如果兑换按钮颜色和形状稳定，可以先：

```text
颜色快速筛选
→ 得到少量候选
→ 小区域模板确认
→ tap
```

这可能比完整模板搜索更快。

---

### E. OCR

只在：

- Accessibility 没节点；
- 模板因版本更新失效；
- 页面出现未知结构；

时作为兜底和诊断工具。

---

## 3. 点击延迟不能靠猜

Node-01 已 Root。

可能的输入路径包括：

```text
Accessibility click
RootAutomator
shell input tap
其他 Root 直接输入路径
```

不要预设 Root 一定最快。

应该在 K20 Pro 上做 benchmark。

### 建议测试

固定一个测试页面。

每种方案重复多次，记录：

```text
T_command
= 发出点击动作的时间

T_visual
= 画面首次可确认变化的时间

latency
= T_visual - T_command
```

最终只保留 Node-01 实测最快、最稳定的路径。

---

## 4. 真正的大延迟可能在刷新

抢券总链路：

```text
T0：目标刷新时刻

下拉手势开始
↓
手势释放
↓
拼多多发刷新请求
↓
服务端响应
↓
页面重绘
↓
5元券出现
↓
识别
↓
tap
↓
兑换请求
```

我们能控制的主要是：

- 手势释放时机；
- 页面变化检测；
- 识别；
- tap。

其中：

> “服务端返回 + 页面重绘”很可能比最后 tap 慢得多。

所以不要只优化 OCR / click。

后续实测需要把各段时间都打日志。

---

## 5. 抢券前预热

不要到 09:00 才启动一切。

建议：

```text
08:59:40
→ Supervisor 抢占任务
→ 停止游戏
→ 打开目标页面
→ 保持屏幕亮
→ 初始化 runtime
→ 预加载模板
→ 初始化 Root 输入
→ 申请好截图权限
→ 等待
```

关键时刻只执行：

```text
refresh
→ detect
→ tap
```

不要再做：

- 加载模板文件；
- 初始化 OCR；
- 申请截图；
- 启动自动化服务；
- 打开多层页面。

---

## 6. 刷新时机需要实验校准

如果实测：

```text
手势释放
→ 请求真正到达服务端
```

存在稳定延迟，那么可以研究提前释放。

但：

> **提前多少必须通过 Node-01 + 当前网络 + 当前拼多多实测。**

不能写死“提前 100ms”之类未经验证的数字。

---

## 7. 一天一次状态

持久状态：

```json
{
  "date": "YYYY-MM-DD",
  "claimed_today": true
}
```

如果 09:00 成功：

```text
16:00 不再抢
21:00 不再抢
```

如果失败：

```text
claimed_today=false
→ 下一个刷新点继续
```

“成功”不能只等价于“点过兑换”。

必须尽量通过真实 UI 结果确认：

- 已兑换；
- 已领取；
- 券到账；
- 当日不可再兑换；

之一。

---

## 8. 与游戏的调度

PDD 是高优先级短任务。

典型切换：

```text
GAME
↓
PDD_PREPARE
↓
PDD_CLAIM
↓
RECOVERY
↓
GAME
```

抢券失败也必须有退出条件。

不要因为“没识别到券”而无限刷新，导致游戏永远无法恢复。

---

## 9. 第一轮实机勘察清单

真正写最终脚本前，先采证据：

1. 目标页面截图；
2. Accessibility / UI tree；
3. 下拉刷新前后截图；
4. 09/16/21 点附近模块的不同垂直位置；
5. 目标券出现时的券卡片局部；
6. “兑换”按钮局部；
7. 成功兑换后的页面；
8. 失败 / 已抢完 / 已兑换状态；
9. 点击路径 latency；
10. refresh 到目标出现的 latency。

第一轮目标不是“马上抢到券”。

而是：

> 找到最快、最稳定、最少猜测的关键路径。

---

## 10. 当前主链路假设

在实机证据出现前，当前假设顺序：

```text
Accessibility 可用？
├─ YES
│   → semantic locate
│   → fastest verified tap
│
└─ NO
    → screenshot ROI
    → template / color locate
    → relative tap
    → OCR fallback
```

这条假设以后允许被真实设备证据推翻。
